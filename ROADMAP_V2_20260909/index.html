    Roadmap pós-1.0 — como melhorar o MYCELIUM mais ainda

    Data: 2026-09-09 · Parte de: v1.0.0 (Fases 1–3 completas, Fase 4 fechada — ver docs/GATE_FASE4_20260909.md).

    A tese central (leia primeiro)

    A v1.0.0 é uma ferramenta terminada com zero usuários. O gargalo do projeto não é feature — é distribuição e validação. Todo item deste roadmap está ordenado por uma pergunta: "isso aumenta a chance de alguém real usar e dar feedback?". Features sem usuário são estoque parado; feedback sem ferramenta estável é ruído. A 1.0 resolveu a segunda metade. Este roadmap resolve a primeira.

    Se só fizer 3 coisas: Fase 0 → PR EC3 → init wizard. Todo o resto é opcional.

    Horizonte 0 — Destravar distribuição (dias, mantenedor)

    Sem isto, nada abaixo importa. É o único horizonte sem gate — é pré-requisito.

    # Item Esforço Pronto quando
    H0.1 Fase 0: upload PyPI + push GitHub + CI real verde 1–2 h pip install mycelium-accel funciona numa máquina limpa
    H0.2 Publicar docs site (gh-pages ou ReadTheDocs) 1 h URL pública no README
    H0.3 Abrir PR EC3 (docs/EC3_PR_PACK.md) + anúncio (docs/ANNOUNCEMENT_DRAFT.md) 1 h links registrados
    H0.4 Registrar feedback externo (meta: 3) dias 3 entradas datadas (issue/comentário/email)

    Métrica de saída do H0: instalação limpa OK + CI real verde + ≥1 reação externa. Se H0 falhar (ex.: PyPI bloqueia o nome, CI quebra no macOS real): corrigir é a prioridade absoluta; H1 nem começa.

    Horizonte 1 — v1.x a partir do uso real (semanas)

    Só priorizar depois do H0. Ordem sugerida — cada item responde a uma fricção que usuários reais vão encontrar nos primeiros 30 minutos:

    • v1.1 — onboarding (fricção: "como começo?")
    • mycelium-accel init: gera mycelium.target.json + 1 variante-exemplo a partir de perguntas (comando de benchmark? métrica?).
    • Quickstart < 5 min cronometrado: do pip install ao primeiro HTML.
    • doctor sugere correções (--fix para o trivial: seed_env, allowlist).
    • v1.1 — generalidade (fricção: "funciona no MEU caso?")
    • +2 alvos-exemplo realistas e distintos (ex.: lib Python pura; projeto C com Makefile). Cada exemplo novo é um teste de fumaça da generalidade — se o harness não serve para ele sem gambiarra, o bug é do harness.
    • Meta honesta: 2º caso externo replicado (EC4 — outro projeto real, outro speed-up medido com o mesmo rigor do EC3).
    • v1.2 — robustez estatística (fricção: "posso confiar?")
    • Detector de flakiness: variância entre seeds anômala → aviso no relatório ("repetir com mais seeds antes de aplicar").
    • Regra de warmup adaptativo pré-registrada (cuidado: nada de p-hacking — a regra entra no doc de API antes de entrar no código).
    • v1.2 — HTML histórico (fricção: "melhorei ou piorei desde o mês passado?")
    • Comparar sweeps ao longo do tempo (mesmo alvo, N datas): small multiples + linha de tendência. Reaproveita export_html.
    • v1.3 — modo CI/regressão (vira outro produto: guarda de performance)
    • accelerate --fail-on-regression 5%: exit ≠ 0 se o candidato atual perde >5% do baseline registrado. É o caso de uso que mais gera adoção recorrente (roda todo PR, não uma vez).

    Métrica de saída do H1: instalações/semana > 0 consistente + ≥3 issues qualificadas + EC4 publicado. Kill: se após H0+H1 ninguém além do mantenedor rodou o accelerate, o problema é posicionamento, não feature — parar H2 e reescrever o anúncio/README antes de codar mais.

    Horizonte 2 — apostas v2.0 (meses, cada uma com gate próprio)

    Regra: uma aposta H2 só começa se ≥3 usuários pediram ou 1 pagaria/usaria em produção. Sem isso, é invenção de roadmap — o projeto já matou C1/C3 por menos.

    Aposta O que muda Risco principal
    A. Sugestão automática de variantes produto passa de "mede" para "propõe + mede". Começar por heurísticas estáticas (flags de compilador, -O sweep, env knobs); LLM opcional depois, sempre atrás do sandbox+allowlist existentes virar gerador de ruído: sugestões ruins queimam a confiança que a 1.0 construiu
    B. Sweep distribuído workers remotos (SSH/containers) para matrizes grandes complexidade operacional >> ganho para 95% dos usuários; só com demanda provada
    C. Plugin API estável entry points para metrics_parser e variant modes de terceiros API prematura congela o design errado — esperar 2–3 parsers reais antes
    D. Limpeza 2.0 (prometida) remover alias mycelium, dropar Pythons EOL baixo — é obrigação assumida em API_STABLE_1.0.md

    Anti-metas explícitas (não fazer): - Não virar framework de ML/AutoML — o diferencial é medir honestamente, não adivinhar. - Não suportar Windows além do CI sem demanda real (custo de manutenção > benefício hoje). - Não reescrever em Rust/C "por performance" sem profiling: o custo está nos benchmarks do usuário, não no harness (dogfood: 75 rps no harness vs segundos por benchmark real). - Não adicionar telemetria de uso sem opt-in explícito (quebra a confiança do nicho).

    Trilha pesquisa (GATED — só abre com o gate da Fase 4 verde)

    Nada aqui executa antes de: 1.0 publicado + ≥3 externos + sobra de horas (docs/GATE_FASE4_20260909.md). Quando abrir, a ordem é por "pista mais quente":

    1. R0. Replicação de C3 com poder — o p=0.076 inconclusivo é a pista mais quente do projeto. Pré-registrar N para poder 0.8 no efeito observado, rodar uma vez, aceitar o veredito (vida ou morte, sem re-análise).
    2. R1. C-a e C-b — já pré-registrados com kill definido (ver gate doc).
    3. R2. Scaling study (capability × compute) — só se R0 ou R1 viverem.
    4. Regra permanente: 1 claim por experimento, kill pré-definido, mortes arquivadas e documentadas (ADR-0002/R8 continua valendo).

    Saúde contínua (todo horizonte, todo mês)

    • Deps atualizadas + ci_local.sh verde; Pythons suportados acompanham upstream.
    • Segurança: allowlist/sandbox revisados a cada feature que toca execução.
    • Docs vivas: cada feature nova atualiza site + API doc (nunca "depois").
    • Dogfood permanente: gate ≥70 rps roda sempre; queda >10% bloqueia release.
    • Revisão deste roadmap: mensal, 30 min — matar itens sem tração é sucesso, não fracasso.
